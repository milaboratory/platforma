Block action context in templates. `render()` sets the action context of the rendered template from the action context of the current renderer: a new `ActionContext` with a copy of the parent context baggage and its own `name` (the imported template name, or the new `name` option), linked from the parent context; a new sinkhole with the same baggage when the current renderer is in the sinkhole; nothing when it has no action context. The link is the render's optional `actionContext` service field, set once, so the template cannot change it. `render(tpl, inputs, { actionContext: false })` puts a template and everything below it into the sinkhole: reports are dropped, but the baggage passes down. `self.actionContext()` and `smart.resource.actionContext()` return a handle with `record(namespace, state, ...detail)` and `setReading(namespace, key, value)`, which write to the context with `tx.resourceKeyValueSetAsync`; `self.actionContext().baggage()` returns the baggage of the current context or sinkhole (e.g. `run-id`, `block-id`), and `render(tpl, inputs, { actionContext: { ...baggage } })` gives a render a new action context, for templates rendered outside a block. Exec and workdir resources a template creates (ComputeRequest, RunCommand, WorkdirFill, WorkdirSave) are linked to the template's action context with `actionContext.inherit(rid)`, so the runner and the data controller report into it. Every link is created in the transaction that creates the resource, before its inputs are locked. Everything is a no-op unless the backend has the primitives (`feats.kvAsync`, `feats.optionalFieldsInSchemas`).
